# 指定用户赠金核销方案

状态：2026-11-18 本地实现与测试；默认关闭，未部署、未为生产用户启用。

## 目标

针对已明确同意此规则的指定用户，提供默认关闭的赠金核销功能。
充值本金 100、赠金 10，实际余额消费 10 时另行核销赠金 1。
模型消费仍记 10；核销独立记账，不修改模型费用、API Key 配额或模型使用记录。
用户界面不新增核销流水列表；管理员可查看完整流水和启用依据。
产品展示不能把会被核销的赠金描述成额外可消费本金。

## 管理配置

- 用户管理中按账号启用，默认关闭；记录操作者、用户同意备注、生效时间。
- 可设置核销总额上限；比例来自各笔已成功充值的本金和赠金快照，不能随全站活动配置变化。
- 生效时间决定哪些消费开始触发核销，不按时间直接扣本金。
- 关闭后停止新核销，不回补已核销金额；补偿通过独立有审计的调整完成。
- 与现有“不参与充值优惠”开关区分：后者不赠送，前者赠送后按约定核销。

## 资金规则

- 每笔符合条件的成功充值创建独立批次：本金初值、赠金初值、本金已用、赠金已核销、退款状态。
- 采用确定的批次消耗顺序；历史余额与其他资金来源必须明确归属，不能把所有余额消费都视为本批次本金消费。
- 单批次累计目标核销额 = 累计本金消耗 / 初始本金 * 初始赠金。
- 本次核销 = 本次消费前后累计目标的差额，受该批次未冻结的剩余赠金、可用余额及账户配置剩余上限限制；不追补之前因限额或关闭而跳过的金额。
- 使用定点十进制，累计计算消除小额请求舍入误差；批次本金耗尽时核销尾差。
- 不得超出对应批次赠金余额，不得将本金、签到奖励或其他赠金作为核销来源。
- 仅余额支付部分触发；订阅消耗、失败请求、重复上报不触发。
- 退款尝试进入 REFUNDING 时，按原批次一次性返还此前核销金额并永久终止该批次；部分退款或退款失败也不会重新核销，保守保留用户权益。原退款扣减计划不因此扩大。
- 非模型消费的余额减款（包括手工调整、退款扣减）会终止该用户现有批次，避免资金归属不明时继续核销；不会追补。

## 一致性与审计

- 充值入账与批次创建处于同一事务，重复支付回调不能重复创建批次。
- 消费、批次消耗、赠金核销及独立审计流水必须原子提交。
- 单笔、批量及历史扣费入口必须统一规则，并发按用户序列化或持有一致的行锁。
- 核销使用消费结算唯一标识去重，重试不重复扣减。
- 审计含用户、充值批次、关联消费、核销金额、比例快照、时间、前后余额和配置版本。
- 管理员权限控制，普通用户 API 不暴露管理员备注或其他用户记录。
- 余额缓存、低余额判断与通知须使用核销后的余额。

## 验收

- 默认关闭时现有充值与扣费行为不变。
- 100 + 10 批次消费本金 10，消费流水 10、独立核销流水 1。
- 完整消耗本金 100 时累计核销恰好 10。
- 覆盖多档比例、多次充值、混合历史余额、部分退款、重复回调、重复消费、并发批处理、微额舍入、开关切换与生效边界。
- 不以真实生产账户进行试扣，不在测试通过前部署或启用。

## 已确认范围与执行边界

用户确认首版仅处理新充值，不追溯、拆分或补扣历史赠金。

- 默认关闭；仅管理员为已同意的指定账号启用。
- 资格同时要求订单创建、成功入账均发生于本次启用及设置的生效时间之后。
- 启用前已创建但尚未支付的订单仍按原规则处理，避免改变已有订单约定。
- 不为历史支付订单、兑换码、签到、手工加款或邀请返利自动创建核销批次。
- 历史余额及其他非核销资金先正常消费，再按到账先后消费符合条件的新充值批次。
- 同一订单重复回调、补发到账和对账重试共用原批次，不新建重复批次。
- 开启前已冻结的图片任务资金属于原资金，不得在稍后结算时算作新充值本金。
- 关闭后不补扣；重新开启不追溯关闭期间的充值或消费。
- 每次独立保存配置都会生成新版本并终止旧批次，包括修改时间、上限或备注；界面明确提示这一行为。订单创建时记录版本，入账时必须匹配同一有效版本，避免时钟偏差使旧订单加入。
- 新图片任务按批次登记冻结资金，并同时冻结预计核销赠金；实际结算按原冻结归属核销，取消释放全部冻结金额。启用前冻结任务不核销。
- 保留既有模型实际费用结算的透支策略；本功能不额外透支余额，无法覆盖的核销不追补，也不能替代模型请求的预估费用限制。
- 原始赠送比例按订单快照计算：本金 = 到账总额 - 赠金；不得用含手续费的实付金额替代本金。
- 达到核销上限后停止核销，剩余赠金保留；修改上限不追补此前未核销的消费。
- 不自动迁移任何真实账号到此模式，不包含生产启用或发布。

## 实施顺序

1. 建立配置版本、充值批次和独立审计表，历史数据零回填。
2. 在兑换入账事务内登记新充值批次，与支付重试共用幂等边界。
3. 统一单笔、批量、图片冻结/确认及旧消费入口；保证消费与核销原子提交。
4. 接入退款/消费冲正，按原批次退回或取消剩余核销权利。
5. 在用户编辑页加入开关、生效时间、核销上限、同意备注和管理员流水入口。
6. 完成真实 PostgreSQL 并发/重试/退款测试和前端交互测试后，再进入发布流程。
