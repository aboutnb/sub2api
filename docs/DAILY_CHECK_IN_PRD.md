# 每日签到功能 PRD

> 文档状态：实现稿，待上线验收  
> 版本：v2.2
> 日期：2026-07-26  
> 适用项目：Sub2API 标准模式  
> 产品名称：每日签到（代码统一使用 `checkin` / `check_in`）

## 1. 方案结论

本版本按 `xuya-dev/sub2api` 当前 `main` 的签到逻辑对齐：每日一次、普通/运气两种模式、服务端随机余额、签到历史。**不赠送并发数，不修改用户并发配置。**

| 决策项 | 结论 |
| --- | --- |
| 用户入口 | Header 余额金额前的签到快捷入口，进入独立 `/checkin` 页面 |
| 发放频率 | 每个符合资格的登录用户、每个服务端业务日最多成功一次 |
| 模式 | 普通签到 `normal`、运气签到 `lucky`；两种模式有独立开关，请求必须显式传模式 |
| 普通奖励 | 在 `normal_min` 与 `normal_max` 之间使用服务端密码学安全随机数 |
| 运气奖励 | 管理员独立配置正向结果概率，并可选“余额比例”或“固定金额”区间；服务端先抽方向、再抽幅度，余额不能被扣到 0 以下 |
| 展示 | 签到前不展示奖励金额或正向概率；运气签到的倍率模式仅在二次确认中展示可能倍率范围，成功后展示实际到账金额和模式 |
| 日期 | 复用系统全局 IANA 时区，默认 `Asia/Shanghai`；浏览器时区不参与判定 |
| 幂等 | `(user_id, checkin_date)` 唯一约束；重复请求返回原记录，不重复改余额 |
| 历史 | 当前服务端自然月真实日历 + 分页历史记录 |
| 管理入口 | 独立 `/admin/checkin`，配置开关、普通区间、运气结算方式及区间、今日概览和发放记录 |
| 并发 | 签到不赠送并发，不修改 `users.concurrency`、API Key 并发或订阅额度 |
| 防批量 | 默认要求账号满 24 小时；同一可信来源 10 分钟最多 20 个不同账号首次领取 |
| 安全防护 | 始终启用每账号/可信来源请求频控、幂等键、严格请求解析、事务结算、数据库完整性约束和安全审计 |
| 默认状态 | 全局签到升级后关闭；两种模式开关默认开启，不改变现有实例行为 |

## 2. 参考项目对照

已核对参考仓库 `xuya-dev/sub2api` 当前 `main`（HEAD `37fe94478ad2f979d7240090f48557c4af301039`）：

- `checkin_records` 以 `(user_id, checkin_date)` 唯一，保证每日一次。
- `POST /checkin` 接收 `normal` 或 `lucky` 模式。
- 普通模式随机抽取金额；运气模式在整个最小至最大倍率区间均匀抽取，因此正负区间宽度会隐式影响正向概率，最终余额不得小于 0。
- `GET /checkin/status` 返回当天状态，`GET /checkin/records` 返回分页历史。
- 签到日期使用服务端配置时区。
- README 中的 `user_concurrency` 是独立的用户并发上限配置，不是签到奖励。

本项目沿用参考项目的每日一次、普通/运气模式和签到历史，但将运气签到改为独立概率与正向阶梯模型：先按配置概率抽取正负方向；正向命中后按自定义阶梯权重选择区间，再从区间内的两位小数档位等概率抽取；负向在配置范围内的两位小数档位等概率抽取。倍率或金额边界不再影响方向概率。同时保留此前确认的体验约束：快捷入口位于余额前、独立签到页、真实月历、用户侧不重复展示时区、不使用“随机到账”措辞、签到前不展示今日可得金额。

## 3. 目标与非目标

### 3.1 产品目标

1. 用户可以从余额前的快捷入口进入独立签到页，选择一种签到方式并领取当日余额结果。
2. 同一账号同一业务日只能产生一条权威记录，重复点击、多标签页和多实例重试都不重复发放。
3. 用户可查看真实服务端自然月日历和历史记录，知道哪些日期已签到及实际到账金额。
4. 管理员可以独立开关全局签到、普通签到和运气签到，调整两种模式的参数并查看签到发放数据。
5. 签到余额奖励与充值、兑换、邀请返利、支付订单、订阅权益和并发配置隔离。
6. 限制短时间内从同一来源操控多个账号领取，不以全站人数或每日预算限制正常用户。

### 3.2 非目标

- 不赠送并发，不增加或临时提高任何用户、API Key、账户或平台并发上限。
- 不设置每日预算、抢名额、容量限制或“预算耗尽”页面。
- 不做连续签到阶梯、补签、自动签到、排行榜、积分、任务中心或抽奖活动。
- 不把运气模式包装成保证收益；运气模式可能得到负奖励，必须在确认前明确提示。
- 不接入统一余额总账；签到记录是签到事实，统一余额流水另行建设。

## 4. 用户与权限

用户首次领取需同时满足：JWT 有效、账号 active、standard mode、当前余额非负、全局签到与所选模式均已启用、当天尚无记录，并通过接口安全和防批量规则。当天已有记录不受之后调整的模式开关、账号年龄或来源窗口影响；使用同一幂等键重试直接返回原响应，使用不同键高频重试仍受始终开启的接口频控保护。

管理员登录用户端后也可参与签到；管理配置与用户领取权限相互独立。停用账号和 simple mode 用户不可领取。

## 5. 业务规则

### 5.1 模式与奖励

#### 普通签到 `normal`

- 服务端从闭区间 `[normal_min, normal_max]` 中抽取金额。
- 默认值建议 `0.01 - 0.05` 个系统余额单位，最多 2 位小数。
- 奖励为正数，客户端不能传入金额、随机数或区间。

#### 运气签到 `lucky`

- 服务端先按 `lucky_positive_probability` 独立抽取结果方向；默认正向概率为 `65%`，该概率不随倍率或金额区间变化。
- `lucky_reward_type=multiplier` 时，正向结果按 `lucky_multiplier_positive_tiers` 抽取，负向结果从 `[lucky_min_multiplier, -0.01]` 的两位小数档位等概率抽取，`reward = round(balance_before * multiplier, 2)`。
- `lucky_reward_type=amount` 时，正向结果按 `lucky_amount_positive_tiers` 抽取，负向结果从 `[lucky_amount_min, -0.01]` 的两位小数档位等概率抽取固定金额，该金额不与签到前余额成比例。
- 默认使用 `multiplier`，倍率区间为 `-0.08 - 0.20`，正向阶梯为 `0.01-0.10 / 0.11-0.15 / 0.16-0.20`，权重为 `70/20/10`；金额模式的默认区间为 `-0.05 - 0.10`。上下限只控制幅度，不参与方向概率计算。
- 若 `balance_before + reward < 0`，将奖励修正为 `-balance_before`，保证 `balance_after >= 0`。
- 余额为 0 时运气签到结果为 0；仍然创建签到记录，避免同日重复尝试其他模式。
- 项目余额模型允许负数；负余额账号不得签到，避免奖励或向零截断逻辑意外消除欠额。服务入口和事务锁定用户行后均需复查。
- 运气签到必须经过二次确认。用户端不展示正向结果概率；倍率模式展示可能倍率范围和余额可能增加或减少的风险，固定金额模式不展示金额区间或预估金额。

两种模式均使用 `crypto/rand` 或等价密码学安全随机源。服务端保存 `reward_type` 和 `random_value`，金额型记录的 `random_value` 是抽取金额，倍率型记录的 `random_value` 是抽取倍率；客户端只能传 `mode`。

正向阶梯算法：

1. 设正向总概率为 `P`，第 `i` 个阶梯权重为 `w_i`，全部正向阶梯权重之和为 `W`。
2. 第 `i` 个阶梯的实际概率为 `P_i = P * w_i / W`。管理员修改 `P` 或任一权重后由管理端实时计算展示，不单独保存 `P_i`。
3. 阶梯内以 `0.01` 为步长生成整数档位。若第 `i` 个阶梯包含 `N_i` 个档位，则阶梯内每个具体结果的总概率为 `P_i / N_i`。
4. 负向总概率为 `100% - P`，在负向范围包含的所有 `0.01` 档位中等概率分配。
5. 示例：`P=60%`，正向阶梯为 `0.01-0.10 / 0.11-0.15 / 0.16-0.20`，权重为 `70/20/10`，三个阶梯实际概率分别为 `42%/12%/6%`。

### 5.2 配置

配置沿用现有 `settings` 表键名：

```json
{
  "checkin_enabled": false,
  "checkin_normal_enabled": true,
  "checkin_lucky_enabled": true,
  "checkin_normal_min": "0.01",
  "checkin_normal_max": "0.05",
  "checkin_lucky_reward_type": "multiplier",
  "checkin_lucky_positive_probability": "65",
  "checkin_lucky_multiplier_positive_tiers": "[{\"min\":\"0.01\",\"max\":\"0.10\",\"weight\":\"70\"},{\"min\":\"0.11\",\"max\":\"0.15\",\"weight\":\"20\"},{\"min\":\"0.16\",\"max\":\"0.20\",\"weight\":\"10\"}]",
  "checkin_lucky_amount_positive_tiers": "[{\"min\":\"0.01\",\"max\":\"0.10\",\"weight\":\"100\"}]",
  "checkin_lucky_min_multiplier": "-0.08",
  "checkin_lucky_max_multiplier": "0.20",
  "checkin_lucky_amount_min": "-0.05",
  "checkin_lucky_amount_max": "0.10",
  "checkin_risk_control_enabled": true,
  "checkin_min_account_age_hours": 24,
  "checkin_ip_window_minutes": 10,
  "checkin_ip_max_users": 20
}
```

规则：

1. 全局、普通、运气三个开关独立保存并立即生效；参数保存后立即作为新请求的配置使用。
2. `normal_min >= 0`、`normal_max >= normal_min`、`normal_max <= 100`。
3. `checkin_lucky_reward_type` 只能为 `multiplier` 或 `amount`；旧配置迁移后默认为 `multiplier`。
4. `checkin_lucky_positive_probability` 范围为 `0-100`；倍率必须满足 `-1 <= min < 0 < max <= 10`，固定金额必须满足 `-100 <= min < 0 < max <= 100`；超过范围或缺少任一方向时拒绝保存。
5. 每种正向阶梯最多 10 级，必须从 `0.01` 开始、以 `0.01` 连续无重叠地覆盖到对应正向上限；每级权重必须大于 0，权重无需合计为 100，服务端按权重总和归一化。
6. 所有签到配置值最多 2 位小数并以字符串保存在 `settings`；奖励使用十进制定点数结算到 2 位，用户余额和历史事实字段继续使用 `DECIMAL(20,8)` 保存完整账务精度。
7. 参数缺失或损坏时 fail closed：普通用户不可领取，管理员看到稳定校验错误。
8. 配置 PUT 必须提交当前版本和变更原因，并使用现有 step-up 策略；成功后配置版本递增。
9. 时区只读继承系统全局配置，不在签到页另设时区。
10. 防批量开关默认开启；账号年龄范围 `0-720` 小时，来源窗口范围 `1-1440` 分钟，窗口内账号数范围 `1-10000`。
11. 防批量开关关闭时不执行账号年龄和来源窗口检查，但每日一次、权限校验和数据库事务约束始终生效。
12. 来源仅使用可信代理链解析后的标准 IP；Redis 中的来源和用户标识均使用服务端密钥计算 HMAC-SHA256，不保存明文 IP、原始用户 ID，也不使用可枚举的普通哈希。
13. 接口安全频控不能通过防批量开关关闭：每账号默认 1 分钟最多 10 次、每可信来源默认 1 分钟最多 60 次 POST；该硬上限不作为运营活动参数开放修改。
14. 全局签到开启但普通与运气均关闭时，状态返回 `can_check_in=false` 和 `unavailable_reason=no_modes_enabled`；服务端必须拒绝直接提交已关闭模式。

### 5.3 自然日与真实日历

- 服务端使用应用统一时区计算业务日，业务日范围为当地时间 `[00:00:00, 次日 00:00:00)`；浏览器时间不参与判定。
- 前端使用状态/历史接口返回的 `business_date`、`days_in_month`、`first_weekday` 生成月历，不用浏览器本地日期推导签到状态。
- `first_weekday` 使用周一为索引 0 的约定，用户端日历按周一至周日排列。
- 日历只展示当前服务端自然月；没有记录的日期保持中性状态，不称为漏签。
- 用户页面不重复展示时区文本；时区只用于服务端判定和管理审计。

### 5.4 发放与余额口径

- 领取前读取并校验当前配置；领取事务锁定用户行、复查当天记录并计算奖励。
- 余额更新与签到记录写入同一事务；任何一步失败全部回滚。
- 只更新 `users.balance`，不增加 `total_recharged`。
- 不触发邀请返利、充值倍率、手续费、支付订单、兑换码或订阅权益。
- 不写入 `users.concurrency`，不创建任何并发奖励记录。
- 余额缓存失效使用现有鉴权/余额缓存失效机制；缓存不是签到事实源。

### 5.5 幂等与重复请求

- 唯一业务键为 `(user_id, checkin_date)`。
- `POST /checkin` 必须携带最长 128 字节的 ASCII `Idempotency-Key`；前端按用户、业务日和模式保存未确认请求的键，明确成功后删除。
- 请求体最多 1 KiB，只接受单个 JSON 对象和唯一字段 `mode`；未知字段、多个拼接对象、非法模式和超限正文均在结算前拒绝。
- 首次成功返回 `newly_checked_in=true`。
- 同一幂等键重放返回缓存的 HTTP `200` 响应并带 `X-Idempotency-Replayed: true`；新键的低频重复请求返回 `newly_checked_in=false` 和原记录。
- 重复请求不得再次随机、改余额、写记录或触发重复返利。
- 客户端提交期间禁用按钮；重复提交由服务端唯一键和用户行锁兜底。

## 6. 用户体验

### 6.1 入口和页面

- `AppHeader.vue` 余额金额前挂载签到快捷入口；未签到显示“未签到”，已签到显示“已签到”。
- 用户侧栏同时提供“每日签到”入口；公开配置 `checkin_enabled=true` 时显示，不以账号冷却期等临时资格状态隐藏。
- 页面路由变化、窗口重新获得焦点和管理员在当前页保存配置后，重新读取签到状态与公开开关。
- 独立 `/checkin` 页面按参考项目的“渐变余额摘要、两种模式、结果反馈、签到历史”组织，并增加真实自然月日历。
- 顶部摘要只显示当前余额和签到状态，不显示时区、连续天数、并发奖励或预算信息。
- 签到前只显示“未签到”；成功后显示实际金额、模式和到账时间。

### 6.2 模式选择

- 只展示已启用的模式按钮；普通与运气均启用时保持两个平级按钮，单模式时使用单列布局。
- 普通签到按钮文案为“立即签到”，点击后直接提交；运气签到点击后先打开二次确认。
- 运气签到确认框不展示正向结果概率；倍率模式展示可能倍率范围，固定金额模式不展示金额区间；两者都提示余额可能增加或减少且不会低于 0。
- 两个按钮都调用同一个 `POST /checkin`，请求体只传 `{ "mode": "normal" | "lucky" }`。
- 今日已有记录后，模式按钮禁用，只展示已产生的模式和实际结果。

### 6.3 状态

| 状态 | 展示与交互 |
| --- | --- |
| 可签到 | 显示“未签到”和已启用的模式按钮，不展示奖励金额 |
| 运气模式提示 | 二次确认但不展示正向结果概率；倍率模式展示可能倍率范围，固定金额模式不展示金额区间 |
| 无可用模式 | 页面显示“当前没有可用的签到方式”，Header 快捷入口隐藏 |
| 提交中 | 禁用两个按钮，显示局部 loading |
| 成功 | 显示实际金额、模式、最新余额和到账时间 |
| 今日已签到 | 禁用操作，显示原始记录；刷新后仍保持 |
| 功能关闭 | Header 隐藏；直接访问页面显示暂未开放 |
| 账号未到冷却期 | Header 与侧栏入口保留；进入页面后显示账号暂不能参与，不展示具体可领取时间 |
| 同来源账号过多 | 本次领取返回可重试提示，不产生余额或签到记录 |
| 请求过于频繁 | 返回 `Retry-After`，不进入随机生成或余额事务 |
| 风控不可用 | 本次领取失败并提示稍后重试，不绕过校验发放奖励 |
| 结果确认中 | 先 GET 状态确认，不重复发放 |
| 历史加载失败 | 不阻断当天签到，日历区域提供重试 |

## 7. 管理体验

新增独立 `/admin/checkin` 页面，包含：

1. 配置：全局签到开关、普通签到独立开关、运气签到独立开关、普通最小/最大金额、运气正向结果概率、结算方式切换、对应的负向/正向倍率或固定金额边界、正向自定义阶梯及其实时实际概率、防批量开关、最小账号年龄、来源窗口、窗口内最大账号数和变更原因。
2. 今日概览：签到人数、普通模式人数、运气模式人数、正向发放金额、负向调整金额。
3. 发放记录：日期、用户、模式、随机值、发放前余额、奖励金额、发放后余额、时间。

管理端不显示并发奖励、并发容量或临时授予字段。记录只读，不支持补签、删改或批量撤销。

## 8. API 契约

接口沿用项目响应封装：成功响应使用 `{code, data, message}`；错误响应使用 `{code, message, reason}`，其中 `code` 为 HTTP 数字状态码，`reason` 为稳定错误标识。金额沿用现有 JSON number 契约，时间使用 RFC 3339。

### 8.1 状态

`GET /api/v1/user/checkin/status`

```json
{
  "enabled": true,
  "normal_enabled": true,
  "lucky_enabled": true,
  "lucky_reward_type": "multiplier",
  "lucky_min_multiplier": -0.05,
  "lucky_max_multiplier": 0.10,
  "eligible": true,
  "can_check_in": true,
  "unavailable_reason": "",
  "business_date": "2026-07-24",
  "timezone": "Asia/Shanghai",
  "server_time": "2026-07-24T16:20:00+08:00",
  "next_reset_at": "2026-07-25T00:00:00+08:00",
  "checked_in_today": false,
  "today_record": null
}
```

用户状态接口不返回 `lucky_positive_probability`；倍率方式仅返回确认所需的倍率配置，并且不返回普通奖励区间或运气固定金额区间。`unavailable_reason` 可为 `disabled`、`no_modes_enabled`、`not_eligible`、`config_invalid`、`already_checked_in`、`account_too_new`、`negative_balance`。

### 8.2 领取

`POST /api/v1/user/checkin`

请求头必须包含 `Idempotency-Key`，请求体最大 1 KiB，并拒绝 `mode` 以外的字段。

```json
{ "mode": "normal" }
```

成功响应示例：

```json
{
  "newly_checked_in": true,
  "record": {
    "mode": "normal",
    "reward_type": "amount",
    "checkin_date": "2026-07-24T00:00:00Z",
    "checked_in_at": "2026-07-24T16:21:03+08:00",
    "random_value": 0.37,
    "reward_amount": 0.37,
    "balance_before": 1.25,
    "balance_after": 1.62
  }
}
```

运气模式响应同样返回实际 `reward_amount`，可能为负数；`reward_type` 标识 `random_value` 是金额还是倍率。重复请求只将 `newly_checked_in` 改为 `false` 并返回原始结果。

### 8.3 历史

- `GET /api/v1/user/checkin/records?page=1&page_size=20` 返回分页历史；月历复用该接口最近 100 条记录生成。
- 历史项包含 `checkin_date`、`mode`、`reward_type`、`random_value`、`reward_amount`、`balance_before`、`balance_after`、`checked_in_at`。
- 不返回全站预算、并发字段或其他用户信息。

### 8.4 管理配置与记录

`GET/PUT /api/v1/admin/checkin/config` 读写全局与两种模式的独立开关、普通区间、运气正向结果概率、结算方式与两组备选区间、防批量参数；PUT 必须提交完整字段、`expected_config_version` 和 `change_reason`。

`GET /api/v1/admin/checkin/overview` 返回业务日签到人数、模式分布和金额汇总。

`GET /api/v1/admin/checkin/records` 支持日期、用户 ID、邮箱关键字和分页查询；邮箱仅对管理员返回。

稳定错误码：

| HTTP | reason | 场景 |
| --- | --- | --- |
| 403 | `CHECKIN_NOT_ELIGIBLE` | 账号状态或运行模式不具备领取资格 |
| 403 | `CHECKIN_DISABLED` | 功能关闭 |
| 403 | `CHECKIN_MODE_DISABLED` | 请求的普通或运气模式已关闭 |
| 403 | `CHECKIN_ACCOUNT_TOO_NEW` | 账号未达到管理员配置的最小年龄 |
| 403 | `CHECKIN_NEGATIVE_BALANCE` | 当前余额为负，禁止通过签到改变欠额 |
| 429 | `CHECKIN_SOURCE_LIMITED` | 同一可信来源窗口内的不同账号数已达上限 |
| 503 | `CHECKIN_RISK_UNAVAILABLE` | 活动级多账号守卫不可用，不发放奖励 |
| 429 | `CHECKIN_RATE_LIMITED` | 每账号或可信来源的请求频率超过安全上限；响应包含 `Retry-After` |
| 503 | `CHECKIN_SECURITY_UNAVAILABLE` | 请求安全守卫、可信来源或 Redis 不可用，失败关闭 |
| 503 | `CHECKIN_ENTROPY_UNAVAILABLE` | 密码学随机源不可用，事务回滚且不发放奖励 |
| 400 | `CHECKIN_INVALID_REQUEST` | 未知字段、拼接 JSON 或请求结构非法 |
| 413 | `CHECKIN_REQUEST_TOO_LARGE` | 请求体超过 1 KiB |
| 400 | `IDEMPOTENCY_KEY_REQUIRED` | 缺少幂等键 |
| 409 | `CHECKIN_CONFIG_VERSION_CONFLICT` | 配置版本冲突 |
| 400 | `CHECKIN_CONFIG_INVALID` | 金额、倍率或配置结构非法 |

## 9. 数据模型

```sql
CREATE TABLE checkin_records (
    id              BIGSERIAL PRIMARY KEY,
    user_id         BIGINT NOT NULL REFERENCES users(id),
    mode            VARCHAR(20) NOT NULL CHECK (mode IN ('normal', 'lucky')),
    reward_type     VARCHAR(16) NOT NULL CHECK (reward_type IN ('amount', 'multiplier')),
    reward_amount   DECIMAL(20,8) NOT NULL,
    balance_before  DECIMAL(20,8) NOT NULL,
    balance_after   DECIMAL(20,8) NOT NULL,
    random_value    DECIMAL(20,8) NOT NULL,
    calculation_scale SMALLINT NOT NULL CHECK (calculation_scale IN (2, 8)),
    checkin_date    DATE NOT NULL,
    checked_in_at   TIMESTAMPTZ NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL,
    CONSTRAINT checkin_records_user_date_unique UNIQUE (user_id, checkin_date)
);
```

记录保存当时的业务日期、模式、结算类型、随机值、奖励、计算精度和余额前后值，历史不随当前配置变化。新签到的 `calculation_scale=2`，历史记录保留 `8`；旧普通记录迁移为 `reward_type=amount`，旧运气记录保持 `multiplier`。签到记录不是充值流水；用户物理删除时随用户级联清理。

## 10. 原子事务与缓存

首次领取顺序：JWT 校验 -> 严格解析请求 -> 幂等协调 -> 始终开启的账号/来源请求频控 -> 校验用户 -> 查询当天记录 -> 加载配置 -> 检查账号年龄 -> Redis 原子登记来源窗口账号 -> 开启事务 -> 锁定普通用户行 -> 复查当天记录 -> 生成密码学随机数 -> 更新余额 -> 插入签到记录 -> 提交 -> 尽力失效余额缓存。

事务不变量：

1. 余额更新与签到记录在同一数据库事务提交。
2. 任一步失败全部回滚。
3. 重复请求不重新随机、不再次更新余额。
4. 提交后缓存失效失败不回滚数据库事实；缓存按现有过期策略收敛。
5. 余额扣费与签到通过用户行锁串行化，最终余额等于原余额 + 签到奖励 - 实际扣费。
6. 密码学随机源失败时不得回退到最小值或固定值，必须返回 503 并回滚。
7. 数据库约束复核模式、随机值、奖励边界和前后余额守恒，异常写入直接失败。

## 11. 风控、观测与验收

### 11.1 风控

- 运气模式可能产生负奖励，用户确认前必须明确提示；不能用“稳赚”“保底”等文案。
- 账号冷却期默认 24 小时，降低即时批量注册后领取的收益；管理员可在 `0-720` 小时内调整。
- Redis Lua 使用 `SADD + SCARD + PEXPIRE` 原子维护同一来源窗口内的不同 `user_id`；默认 10 分钟最多 20 个。
- 同一用户在同一来源重复进入守卫不增加计数；超过上限的新用户从集合移除，避免失败账号持续占用共享出口容量。
- 来源 IP 通过安全解析函数获得并在写 Redis 前标准化；Redis key 和集合成员只包含带服务器密钥的 HMAC-SHA256，窗口到期自动删除。
- 活动级多账号守卫只针对潜在首次结算；当天已有签到记录不再登记来源窗口账号。除幂等缓存直接重放外，所有通过结构校验的签到 POST 均在读取用户状态前计入账号和可信来源频率。
- Redis 异常、守卫未注入或可信 IP 无法解析时 fail closed，返回 `503 CHECKIN_SECURITY_UNAVAILABLE`，不发放奖励；活动级多账号守卫自身不可用时返回 `503 CHECKIN_RISK_UNAVAILABLE`。
- IP 仅是短窗口来源信号，不作为自然人身份或永久封禁依据；共享网络中的正常用户可在窗口结束后重试。
- 管理员可作为登录用户签到，也可管理配置；管理端不能补签、删记录或直接扣款。
- 正向奖励不增加 `total_recharged`，不触发返利或支付逻辑。

### 11.2 安全防护

- 用户接口只接受 Bearer JWT，用户 ID 始终取认证上下文，客户端不能指定代领账号；停用、删除及已撤销会话均无法领取。
- 负余额账号在入口与事务内双重拒绝，防止签到把既有欠额截断为零；数据库也拒绝负数 `balance_before` 的签到事实。
- 后台配置只对管理员开放，PUT 额外要求 step-up 2FA；配置采用版本比较更新，防止并发覆盖。
- 始终开启的 Redis Lua 请求守卫同时限制账号和哈希来源。单个账号达到上限后的请求不再消耗共享来源额度，降低恶意账号阻断共享网络的风险。
- 安全守卫、可信来源解析或 Redis 不可用时 fail closed；运营防批量开关只控制账号年龄和多账号领取规则，不能关闭接口安全层。
- 幂等协调器在服务端先将客户端键绑定认证用户，再按路由和请求体校验重放；不同用户的相同客户端键互不冲突，相同用户同键不同载荷返回冲突，相同载荷返回首次结果。
- 请求解析使用 1 KiB 上限和未知字段拒绝策略，防止超大正文、参数夹带和多个 JSON 对象造成歧义。
- 用户行锁、同日唯一键、同事务余额更新/记录插入及数据库 CHECK 约束共同保证并发与结算完整性。
- 密码学随机源异常时失败关闭，不使用可预测的默认奖励；客户端不能提交金额、倍率、随机值、余额或业务日期。
- 用户签到 POST 和管理员配置 PUT 均进入现有审计日志；审计记录动作、操作者、结果、稳定错误码和请求 ID，不记录 JWT、完整凭证或 Redis 明文来源 IP。
- 全局 HTTP 服务继续提供请求头大小、读取超时和总正文上限；签到端点使用更小的专属正文上限。

### 11.3 后续增强

- 将金额 API 统一升级为十进制字符串，并替换现有余额计算的 `float64` 边界。
- 将业务日计算下沉到 PostgreSQL，消除跨午夜长事务的应用取时窗口。
- 为签到记录增加配置版本、请求 ID，并将配置变更原因写入独立审计表。
- 为缓存失效增加事务 outbox 和重试 worker。
- 增加尝试结果、奖励金额、接口耗时和缓存失效失败指标。

### 11.4 验收标准

- 同一用户 20 路并发 POST 只有一条记录、一次余额变化。
- 普通模式随机值落在配置区间，奖励金额等于随机值。
- 运气签到先按独立概率决定正负方向；修改倍率或金额边界后，同一概率配置下的正向样本占比不变。
- 运气倍率方式的随机值落在所选方向的非零倍率半区，奖励等于余额 × 倍率，余额永不小于 0。
- 运气固定金额方式的随机值落在所选方向的非零金额半区，奖励与签到前余额无比例关系，负值最多扣至余额 0。
- 非法结算类型、概率超过 `[0, 100]`、倍率未满足 `-1 <= min < 0 < max <= 10` 或金额未满足 `-100 <= min < 0 < max <= 100` 时拒绝保存。
- 运气模式可能为负奖励，页面显示风险提示和最终实际结果。
- 重复 POST 返回 200 原记录，不再次随机或改余额。
- 日历正确覆盖 28/29/30/31 天月份及不同首日星期。
- 管理员登录用户端后可领取；非管理员无法读写管理配置。
- 全局开关与两个模式开关分别生效，关闭模式后其按钮消失且直接 API 请求返回 `CHECKIN_MODE_DISABLED`；两个模式都关闭时不可签到。
- 功能关闭、simple mode、配置损坏时不发放余额。
- 余额为负时返回 403，余额与签到记录均不变化；余额在入口校验后并发变负时事务内再次拒绝。
- 风控开启时，新账号在冷却期内返回 403；达到年龄后可以正常领取。
- 后台开启后，公开设置立即返回 `checkin_enabled=true`，普通用户的 Header 与侧栏均出现签到入口。
- 处于账号冷却期的用户仍能进入签到页，页内展示不可用原因且不允许提交。
- 同一来源上限为 3 时，5 个不同账号依次领取应为前 3 个成功、后 2 个返回 429；已成功账号重复请求仍返回 200 原记录。
- 同一用户重复进入 Redis 守卫不增加来源账号数；窗口 TTL 到期后新账号重新计数。
- Redis 不可用、可信 IP 为空或非法时返回 503，余额和签到记录均不变化。
- Redis 中不出现明文来源 IP，防批量关闭后账号年龄与来源限制停止生效。
- 防批量关闭后接口安全频控仍生效；账号超过 10 次/分钟或来源超过 60 次/分钟返回 429 和 `Retry-After`。
- 单账号被限流后的额外请求不消耗共享来源额度；Redis 安全键不包含明文 IP。
- 缺少/冲突幂等键、未知字段、拼接 JSON、超 1 KiB 正文均在结算前拒绝。
- 密码学随机源失败时返回 503，余额和记录不变化；非法结算记录被数据库约束拒绝。
- 失败事务不留下余额变化或签到记录；缓存失效失败不回滚数据库事实。
- 桌面和 390px 移动端无横向溢出；签到前及运气签到二次确认均不展示正向概率，倍率方式仅展示配置范围。

## 12. 设计稿与发布边界

原型：[docs/checkin-design/index.html](checkin-design/index.html)。

- Header 快捷入口位于余额前，操作集中在独立 `/checkin` 页面。
- 用户页展示普通/运气模式选择，成功态展示实际金额和模式；不展示并发、预算或“随机到账”。
- 管理端展示全局与两种模式的独立开关、普通金额区间、运气正向概率、结算方式切换及对应区间、紧凑的防批量参数区、模式分布和发放记录。
- 功能默认关闭，先灰度验证幂等、运气模式边界、余额事务和缓存收敛，再逐步开放。
